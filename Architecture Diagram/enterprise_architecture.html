Core Concepts

Tenant ID

Identifies the client, company, or application (e.g., TENANT_ABC). Passed via public widget config, but strictly validated server-side against registered domains.

User/Guest ID

Identifies the visitor or user within that specific tenant. Auto-generated or passed via authenticated client sessions.

Conversation ID

Identifies a particular chat session bound to a specific User ID and Tenant ID.

Admin Account

Identifies the person who manages a specific tenant's conversations via the dashboard. Access is strictly scoped to the assigned Tenant ID.

Security Flow

CRITICAL: The backend must not blindly trust a Tenant ID supplied by an untrusted client browser.

Secure Flow:
1. Frontend sends Tenant ID via X-Tenant-ID header.
2. Backend intercepts request using the validateTenantOrigin middleware.
3. It strictly validates the origin domain against the registered Tenant configuration.
4. Resolves authorized Tenant.
5. Executes strictly tenant-scoped database queries (e.g., `WHERE tenant_id = $1`).
6. Returns tenant-scoped response.
Public Widget Integrity: The client browser contains ONLY the public widget configuration (Tenant ID, API URL). It NEVER contains OpenAI API keys, Database credentials, or JWT signing secrets. All sensitive credentials remain securely on the server.

Standardized Integration

We utilize ONE STANDARDIZED INTEGRATION METHOD across all client applications. Whether Client A, B, or C, they all inject the same core chat-widget.bundle.js into their global/root layout, parameterized only by their unique tenantId and environment variables.
